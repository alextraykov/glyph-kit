## How to work

- **Repositories.** The kit is `/Users/atraykov/glyph-kit`. The portfolio's copies (`skills/glyph-kit/`, `public/labs/glyph-kit/`) come from `npm run sync:glyph-kit` and are never edited by hand.
- **One workstream at a time**, in the order below, with one writer. Each workstream gets one commit. Don't push: Alex reviews and pushes.
- **No dependencies.** The same spec always gives the same output. Figures stay within 80 cells and use only measured glyphs.
- **Byte-stable output.** Run `node tools/build-reference.mjs`, then `git diff skills/glyph-kit/reference`. That's the gate: the text form of every shipped example stays exactly as before. Colour changes HTML and the other drawn forms only.
- **Copy.** Plain words, and say "types", not "kinds", in anything new.

What it already does:

## 2. Two colour types

Both go in the Design system area. Both are drawn by code from a spec, fit in 80 cells, and read correctly in plain text. In HTML and the terminal they show the real colours.

**`palette`: a tonal scale.** One row per hue, one cell group per step:

```text
 Blue    50 ██  100 ██  200 ██  300 ██  400 ██  500 ██  600 ██  700 ██
         AA on page from 500 ·········· ▲
 Red     50 ██  100 ██  200 ██  …
```

- **Data:** `{ hues: [{ name, steps: [{ name, value }] }], page? }`. A value is hex or `oklch(…)`.
- **Text form:** the cells stay `██`. A ▲ marks the first step that reads as words on the page (4.5 to 1). `--compact` writes the values instead.
- **Checks:** steps must get steadily lighter or darker; a step that breaks the order is named.

**`colourRoles`: what each colour is for.** A table of role → token → value, with light and dark side by side, and a contrast verdict for each pair:

```text
 role      token            light             dark              
 words     --color-text     ██ #151513  16.8  ██ #f2f0e8  15.1  AAA
 problems  --color-danger   ██ #b8391a   5.1  ██ #ef7c56   6.0  AA
 lines     --color-border   ██ #a3a199   2.1  ██ #5c5b56   1.9  ok
```

- **Data:** `{ roles: [{ role, token, light, dark, use: "words" | "marks" | "lines" }] }`, or read from `design-system.map.json` with `--map`.
- **Verdicts:** use the same thresholds and wording as the colour checks, so the figure and the refusals agree.
- **The kit's own palettes** are shipped as `colourRoles` examples. The guide shows the kit's colours in its own type.

**Tests:** for each type, zero rows, one row, too many rows (cut with "… and N more"), and a value that breaks the order; equal widths; the contrast numbers agree with `guard.mjs`.

## 3. Easier to edit

Three changes, smallest first.

**`glyph-kit check <spec | file.md>` lists every problem at once.** It checks the spec, draws it and runs lint. It lists every problem with where it is and what to change, and exits 1 if there are any. Today an agent finds problems one per render, and the 20 October study showed that costs turns. (This is the `make` / `check` from `docs/ui-system-plan.md` and the canvases study plan, pulled forward.)

**A figure in Markdown keeps its spec, and redraws in place.**

- `render --to markdown` and `export --to md` gain `--with-spec`. It writes the spec as a `json` fence inside `<details><summary>Spec</summary>` right after the figure. A figure can point at a spec file instead: `<!-- glyph-kit: specs/funnel.json -->` on the line above its fence.
- `glyph-kit redraw <file.md>` draws every such figure again:
  - it replaces only each figure's `text` fence;
  - everything else stays byte for byte, including notes and comments between figures;
  - a broken spec leaves its figure alone and is reported with its line.
- `redraw --check` changes nothing. It lists figures out of date with their spec, for CI or a pre-commit hook.

**Edit the drawing, keep the spec** (PLAN.md Next item 3). For the types whose text can be read back without guessing, `glyph-kit read <file.md | figure.txt>` turns an edited drawing back into its spec:

- `table`, `tokenTable`, `decisionLog`, `colourRoles`;
- the QA checklist;
- `nowNextLater`;
- `screen` (one primitive per line).

The new spec is drawn again and compared with the edit. If the two differ, it shows where and changes nothing. Charts aren't read back: you edit their numbers in the spec.

**Tests:**

- `check` lists three problems in one run;
- `redraw` on a file with comments and one stale figure changes only that fence;
- for each readable type: draw, read and draw again gives the same text;
- an edit that can't be read is refused with its line.

## 4. Guidelines for open source

- **README.** A short "Use it" path: install the skill, use it without an agent (the command line), what the MIT licence allows, and how to credit the kit if you want to (it isn't required). Link the three files below.
- **`CONTRIBUTING.md`:**
  - what's welcome: types, fixes, ports, editor and player integrations;
  - what isn't: dependencies, colour as the only signal, glyphs that aren't measured;
  - how to run the checks: `node --test tests/*.test.mjs`, lint and the reference gate;
  - how a change is reviewed;
  - the changelog line every change adds.
- **`docs/adding-a-type.md`.** One worked example, end to end, using `palette` from workstream 2:
  - the registry entry (`label`, `check`, `summary`, `render`);
  - the arrival order;
  - the example spec, from which the guide section is generated;
  - the tests, and the 80-cell and glyph rules.
- **`.github/`:**
  - an issue template for a new type: what it shows, who reads it, a hand-drawn sketch;
  - an issue template for a bug: spec, command, what you saw;
  - a pull request template with the checklist from `CONTRIBUTING.md`.
- **CI:** `ci.yml` also runs lint, the reference gate and `redraw --check` on the guides, so a pull request can't change the drawings by surprise.
